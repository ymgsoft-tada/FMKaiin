# ファンクションキー 設計書

画面下部のファンクションキー表示を、GrapeCity の `GcFunctionKey` から自前のコントロールに置き換えるための設計。

状態: 部品 3 クラスを実装し、`GcFunctionKey` を使っていた 45 フォームすべてを置き換え済み(6 章)。`AppFunctionKey` など旧方式のコードは、使われなくなったが残してある。

---

## 1. 目的と範囲

- 新しいデザイン(白基調・角丸・影付きのボタン)のファンクションキー表示を、共通部品として用意する。
- 既存の `GcFunctionKey` と `AppFunctionKey` を、フォーム単位で 1 つずつ置き換えられるようにする。
- `AppFunctionKey` と `FuncKeyDefine`、Excel から生成している `AppFormFuncKey.cs` は変更しない。

---

## 2. 置き換え前の仕組み

### 2.1 構成

| 要素 | 場所 | 役割 |
| --- | --- | --- |
| `GcFunctionKey` | GrapeCity PlusPak(各フォームの `funckey`) | ボタンの表示と、F キーの検知 |
| `FuncKeyDefine` | comset の `UI/FunctionKeyBinder.cs`(2026-11-26 に、`AppFunctionKey.cs` から移した。名前空間は `ComponentSUI`) | キー 1 つ分の定義(キー・名称・説明・実行するメソッド) |
| `Func○○` クラス | `AppFormFuncKey.cs`(`_doc/AppFuncKey.xlsx` から自動生成) | 画面ごとの `FuncKeyDefine` の一覧。すべて static |
| `AppFunctionKey` | `AppFunctionKey.cs` | `GcFunctionKey` にボタンを並べ、キーに対応するメソッドを実行する |
| `FormFrame` | `FormFrame.cs` | `GcFunctionKey` の `FunctionKeyDown` を受けて `appFuncKey.Exec` を呼ぶ |

フォーム側の書き方:

```csharp
protected override void SetFunction()
{
    appFuncKey = new AppFunctionKey(funckey, FuncMasterBank.Functions);

    FuncMasterBank.RowAdd.Execute = rowAdd;
    FuncMasterBank.Close.Execute = formClose;
}
```

### 2.2 使用状況(置き換え開始前)

| 項目 | 内容 |
| --- | --- |
| 使っているフォーム | 45(すべて `FormFrame` の派生) |
| 使っているキー | F2〜F12。修飾キー(Shift など)付きの定義はない。どの定義も最後は F12 |
| ボタン数 | 1〜5 個がほとんど。最多は FormKaiin の 10 個(幅 1084) |
| 幅が狭いフォーム | FormOutIryoKikan(346)、FormMasterTantosha_DlgPwd(386)、FormMasterTantosha_DlgEntry(401、3 個) |
| `appFuncKey` の使われ方 | `SetEnabled(キー, 可否)` 3 か所、`SetVisible(キー, 可否)` 1 か所。ほかのメソッドはフォームから使われていない |
| `funckey` の使われ方 | `funckey.Select()` 3 か所(表示時) |

### 2.3 課題

1. **見た目**: 新しいデザインの画面に合わない。高さ 25 の細い帯で、ボタンが小さい。
2. **実行するメソッドが static に入る**: `FuncMasterBank.Close.Execute = formClose` は、static な定義オブジェクトにフォームのメソッドを代入している。このため次の問題がある。
   - フォームを閉じて Dispose しても、次に同じ画面を開くまで static から参照され続け、GC で回収されない(画面の種類ごとに 1 インスタンス分)。
   - 同じ定義クラスを使う画面を重ねて開くと、後から開いた画面のメソッドで上書きされる。後の画面を閉じた後に元の画面でキーを押すと、閉じた画面のメソッドが動く。`FuncExcelMenu` は 3 つの画面が共有している。

## 3. 新しい構成

```text
 フォーム
   │  funcKeys = new FunctionKeyBinder(funckey, FuncMasterBasic.Functions);
   │  funcKeys.On(FuncMasterBasic.Save, saveClose);
   ▼
 FunctionKeyBinder (comset の UI)    … AppFunctionKey の代わり
   │  定義(FuncKeyDefine[])からボタンを作り、押されたら対応するメソッドを実行する
   ▼
 FunctionKeyBar (Controls)            … GcFunctionKey の代わり
   │  ボタンの配置と、F キーの検知
   ▼
 FunctionKeyBarButton (Controls)      … ボタン 1 つ分の描画
```

| クラス | ファイル | 代わりになるもの | 役割 |
| --- | --- | --- | --- |
| `FunctionKeyBar` | `comset/UI/FunctionKeyBar.cs` | `GcFunctionKey` | ボタンを並べる帯。F キーが押されたこと・ボタンがクリックされたことをイベントで知らせる |
| `FunctionKeyBarButton` | `comset/UI/FunctionKeyBarButton.cs` | `FunctionKeyButton`(GrapeCity) | ボタン 1 つ。キー名のバッジと名称を描く |
| `FunctionKeyBinder` | `comset/UI/FunctionKeyBinder.cs` | `AppFunctionKey` | `FuncKeyDefine[]` と `FunctionKeyBar` を結び付ける |

- `FunctionKeyBar` は `FuncKeyDefine` を知らない。キーと名称だけを扱う汎用コントロール。
- 「どのボタンを右に寄せるか」「どのボタンを青くするか」は、このアプリの決まりなので `FunctionKeyBinder` が決める。
- `FuncKeyDefine` と `Func○○` クラス(自動生成)はそのまま使う。Excel と生成ツールは変更不要。
- 新旧は共存できる。置き換えていないフォームは、これまでどおり `GcFunctionKey` + `AppFunctionKey` で動く。

## 4. FunctionKeyBar(表示とキー検知)

### 4.1 見た目

| 対象 | 見た目 |
| --- | --- |
| 帯 | 背景は透明(親の背景がそのまま見える)。既定で下端にドッキング(`Dock = Bottom`)。高さ 66(96 DPI 基準) |
| 区切り線 | 画面の内容と帯を区切る、薄い色(214, 221, 230)の 1px の線。帯の上端から 6 下に、帯の幅いっぱいに引く。ボタンは、線より下の範囲の上下中央に置く |
| ボタン | 角丸(半径 8)。白から淡い青灰への縦グラデーション、1px の枠線、下に柔らかい影。中身は 2 段で、高さ 44 |
| キー名のバッジ | ボタンの上段(左右中央)。角丸の小さな枠の中に「F5」などを青い太字で表示 |
| 名称 | ボタンの下段(左右中央)。濃紺の太字。フォントは BIZ UDPゴシック 9.5pt(PC に無ければ Meiryo UI)。バッジとの間は 5 空ける |
| 文字の位置 | キー名と名称の文字は、計算上の位置から 1 下げて描く(BIZ UDPゴシックは文字が上寄りに描かれるため。バッジの枠は動かさない) |
| 強調ボタン | 青のグラデーションで塗り、文字とバッジは白 |
| マウスオーバー | 白いボタンは枠線を青に寄せる。強調ボタンは全体を少し明るくする。どちらも影を濃くする |
| 押下中 | ボタンを影の側へ 1px 沈める |
| 無効 | 文字とバッジをグレーにし、影を薄くする。クリックもキーも反応しない |
| 非表示 | 描かない。その分の場所は詰める |

中身の並べ方は `ButtonLayout` プロパティで選ぶ。既定は 2 段(`Vertical`)。横並び(`Horizontal`。バッジが左、名称が右、ボタンの高さ 36)も選べるが、ボタンの幅を取るので、ボタンの多い画面では名称が収まらない。

色と寸法は `FunctionKeyBarButton` / `FunctionKeyBar` の中の定数で持つ。画面ごとに変える必要が出たら、そのときプロパティにする。区切り線の色だけは `SeparatorColor` プロパティで変えられ、空にすると線を引かない(ボタンは帯全体の上下中央に置く)。

### 4.2 並べ方

- ボタンは追加した順に、左から並べる。
- 「右寄せ」(`Alignment = Right`)にしたボタンは、右端に詰める。右寄せが複数ある場合も、追加した順が左から右になる。
- ボタンの幅は、バッジと名称のうち幅の広い方で決まる(下限 60)。横並びのときは、バッジと名称の幅の合計で決まる。

```text
│ [F5 銀行情報]                             [F11 登録] [F12 キャンセル] │
   ← 左寄せ(追加順)                                  右寄せ(追加順) →
```

どのボタンを右寄せにするかは `FunctionKeyBinder` が決める(5.2)。

### 4.3 幅に収まらないとき

標準の大きさで並べて帯の幅を超える場合は、次の順に試し、収まった段階を使う。

| 段階 | ボタンの間隔 | ボタン内の左右の余白 | バッジと名称の間隔(横並びのみ) | 文字 |
| --- | --- | --- | --- | --- |
| 1. 標準 | 8 | 14 | 8 | 9.5pt |
| 2. 間隔と余白を詰める | 4 | 8 | 8 | 9.5pt |
| 3. 文字を小さくする | 4 | 8 | 8 | 9pt → 8.5pt |
| 4. 限界まで詰める | 2 | 4 | 4 | 8.5pt |

4 でも収まらない場合は、各ボタンの幅を同じ割合で縮め、名称の末尾を「…」で省略する。

置き換えた 44 フォームで確認した結果、2 段の並べ方では、すべてのフォームが 9.5pt のまま(段階 1 か 2)で収まる。いちばんボタンの多い FormKaiin(10 個・幅 1084)も省略なしで収まる。

確認は次の 2 つの条件で行った。どちらも、フォームの大きさはデザイン時のままで拡大されない。

| 条件 | 文字と余白の大きさ | 該当する環境 |
| --- | --- | --- |
| 96 DPI | 等倍 | 表示倍率 100% の PC |
| 120% | 1.2 倍 | カスタム スケーリング 120% の開発 PC で実際に起きている状態(「コントロール・フォーム仕様.md」4 章) |

横並びにした場合は幅が足りず、120% の条件では FormKaiin の名称がほぼすべて省略される(2 段にした理由)。

### 4.4 キー入力

- 帯に登録されているキー(F5・F11・F12 など)が押されると、そのボタンをクリックしたのと同じ扱いにする。
- どのコントロールにフォーカスがあっても反応する。入力欄やグリッドより先にキーを受け取る(F4 でコンボボックスが開く、F2 でグリッドが編集状態になる、といった各コントロールの動作より優先する)。
- 反応するのは、帯を置いたウィンドウがアクティブなときだけ。モーダルの子画面やメッセージ ボックスを開いている間、親画面の帯は反応しない。
- 修飾キー(Shift・Ctrl・Alt)を押しながらの場合は反応しない。
- キーを押しっぱなしにしても、実行は 1 回だけ(自動リピートは無視する)。
- 登録されているキーは、ボタンが無効・非表示でも帯が受け取って捨てる(各コントロールの動作に流さない)。登録されていないキーには何もしない。
- 日本語入力の変換中は、IME がキーを使う(F7 でカタカナ変換など)。この間は反応しない。

**実現方法**: `IMessageFilter` で、ウィンドウに届く前のキー メッセージを見る。フォームの `KeyPreview` や `ProcessCmdKey` を使う方法は、フォーカスのあるコントロールが先にキーを処理してしまう場合があること、フォーム側(`FormFrame`)の対応が必要になることから採っていない。フィルターは帯のウィンドウ ハンドル作成時に登録し、破棄時に解除する。実行するメソッドは、キー メッセージの処理が終わった後で呼ぶ(`BeginInvoke`)。

**F10 について**: `FormFrame` は F10 を `ProcessCmdKey` で無効にしている(メニューへのフォーカス移動を防ぐため)。帯は `FormFrame` より先にキーを受け取るので、F10 を登録すれば F10 のボタンも動く(FormKaiin の「在籍期間表示」)。F10 を登録していない画面では、これまでどおり `FormFrame` が無効にする。`AppFunctionKey` が行っている「F10 のダミー ボタン追加」は不要。

### 4.5 フォーカス

- ボタンをクリックしても、キーで実行しても、フォーカスは移動しない。Tab キーでもボタンには止まらない。
- `funckey.Select()` を呼んでいる既存コード(3 か所)は、そのままでコンパイルでき、エラーにもならない。

### 4.6 公開しているメンバー

| メンバー | 内容 |
| --- | --- |
| `AddButton(Keys key, string text)` | ボタンを追加して返す。同じキーを 2 回追加した場合は例外 |
| `GetButton(Keys key)` | そのキーのボタンを返す。無ければ null |
| `ClearButtons()` | すべてのボタンを取り除く |
| `FunctionKeyPressed` イベント | キーが押された、またはボタンがクリックされたときに発生する。引数にキーとボタンを持つ。ボタンが無効・非表示のとき、帯が無効(`Enabled = false`)のときは発生しない |
| `HandleKeys`(既定 true) | false にするとキー入力を検知しない(クリックだけ受け付ける) |
| `SeparatorColor`(既定 214, 221, 230) | 区切り線の色。空にすると線を引かない |
| `ButtonLayout`(既定 `Vertical`) | ボタンの中身の並べ方。`Vertical` は 2 段、`Horizontal` は横並び |

`FunctionKeyBarButton` の主なプロパティ:

| プロパティ | 内容 |
| --- | --- |
| `Key` | 対応するキー。バッジにはキー名(「F5」)を表示する |
| `Text` | 名称 |
| `Alignment` | `Left`(既定)または `Right` |
| `Emphasized` | true にすると強調ボタンの見た目になる |
| `Enabled` / `Visible` | 標準のプロパティ。変更すると帯が並べ直す |

デザイナーの上ではボタンが無いので、置いた場所が分かるように破線の枠とコントロール名を描く。デザイナーの上ではキーを検知しない。

## 5. FunctionKeyBinder(AppFunctionKey の代わり)

### 5.1 使い方

```csharp
protected override void SetFunction()
{
    funcKeys = new FunctionKeyBinder(funckey, FuncMasterBasic.Functions);

    funcKeys.On(FuncMasterBasic.ShowBank, showBank);
    funcKeys.On(FuncMasterBasic.Save, saveClose);
    funcKeys.On(FuncMasterBasic.Cancel, cancelClose);
}
```

- コンストラクタで、定義の順にボタンを作る。右寄せと強調もここで決める(5.2、5.3)。
- `On(定義, メソッド)` で、キーごとに実行するメソッドを登録する。登録先はこの `FunctionKeyBinder` のインスタンスなので、フォームと一緒に破棄される(2.3 の課題 2 が起きない)。
- 帯の `FunctionKeyPressed` はコンストラクタの中で購読する。`FormFrame` 側での接続は要らない。

### 5.2 右寄せにするボタン

キーボード上で近いキーどうしを、画面でも同じ側にまとめる。

1. 定義の最後が F12 のときだけ、右寄せのボタンを作る。
2. ボタンが 1 つなら、それを右寄せにする。
3. ボタンが 2 つなら、1 つ目を左寄せ、2 つ目を右寄せにする。
4. ボタンが 3 つ以上なら、隣り合うキーの番号がいちばん離れている所を左右の境目にする。
   - 番号が続いている所(F11 と F12 など)は境目にしない。
   - いちばん離れている所が複数あるときは、右側のものを境目にする。
   - すべての番号が続いている場合は、全部を右寄せにする。

| 定義のキー | 左寄せ | 右寄せ | 該当する画面数 |
| --- | --- | --- | --- |
| F12 | — | F12 | 5 |
| F11 F12 | F11 | F12 | 15 |
| F9 F12 | F9 | F12 | 9 |
| F5 F11 F12 | F5 | F11 F12 | 3 |
| F2 F11 F12 | F2 | F11 F12 | 1 |
| F9 F11 F12 | F9 | F11 F12 | 1 |
| F2 F4 F11 F12 | F2 F4 | F11 F12 | 2 |
| F2 F3 F4 F12 | F2 F3 F4 | F12 | 4 |
| F2 F3 F4 F5 F12 | F2 F3 F4 F5 | F12 | 1 |
| F2 F3 F4 F9 F12 | F2 F3 F4 | F9 F12 | 1 |
| F5 F6 F8 F12 | F5 F6 F8 | F12 | 1 |
| F5 F6 F7 F11 F12 | F5 F6 F7 | F11 F12 | 1 |
| F2〜F10 F12 | F2〜F10 | F12 | 1 |

フォームごとに変えたい場合は、ボタンを作った後で `funcKeys.Bar.GetButton(キー).Alignment` を設定する。

### 5.3 強調するボタン

`_doc/AppFuncKey.xlsx` の EnumName 列(`Func○○` クラスのフィールド名)が次のいずれかのボタンを強調する。

| EnumName | 現在の定義 |
| --- | --- |
| `Save` | 登録(F11)。13 画面 |
| `Exec` | 選択実行・作成実行・取込開始・実行(F11。FuncHikiotoshi だけ F5)。7 画面 |
| `Entry` | 現在は該当なし |

対象の名前は `FunctionKeyBinder.EmphasizedNames` に並べてある。増減はここを変える。

EnumName は `FuncKeyDefine` には入っていない。そのため `FunctionKeyBinder` は、渡された配列を `Functions` フィールドに持っているクラスを探し、そのクラスの static フィールド名から求めている。`Func○○.Functions` 以外の配列を渡した場合は、強調なしになる。

### 5.4 実行するメソッドの決め方

キーが押されたら、次の順で探して実行する。

1. `On` で登録したメソッド
2. 無ければ、定義の `Execute`(これまでの `Func○○.Save.Execute = ...` の書き方)
3. どちらも無ければ何もしない

メソッドを実行する前に、フォーカスがあるコントロールに入力の途中の内容があれば、値として確定する(S 系の日付・テーブル コンボの入力欄。`ISEditCommit`。[S画面仕様.md](../control/S画面仕様.md) の 1.3)。ファンクション キーはフォーカスを動かさないので(4.5)、確定しないと、メソッドが「入力する前の値」を読んでしまうため。Gc 系のコントロールには影響しない。

2 を残しているのは、置き換えの手間を減らすため。コンストラクタの 1 行を変えるだけで動き、`Execute` への代入は後から `On` に直せる。ただし 2 の書き方のままだと 2.3 の課題 2 は残る。

### 5.5 AppFunctionKey との対応

| AppFunctionKey | FunctionKeyBinder | 備考 |
| --- | --- | --- |
| `new AppFunctionKey(funckey, 定義)` | `new FunctionKeyBinder(funckey, 定義)` | `funckey` の型が `FunctionKeyBar` になる |
| `Function`(`GcFunctionKey` を返す) | `Bar`(`FunctionKeyBar` を返す) | |
| `Exec(Keys)` | `Exec(Keys)` | 帯が無効のときは実行しない点も同じ |
| `SetEnabled(Keys, bool)` | `SetEnabled(Keys, bool)` | そのキーのボタンが無ければ何もしない |
| `SetVisible(Keys, bool)` | `SetVisible(Keys, bool)` | 同上 |
| `SetEnabled(string, bool)` / `SetVisible(string, bool)` | 用意していない | 名称で指定する版。使用箇所がない |
| `BeforeKeyDown` イベント | 用意していない | 使用箇所がない |
| `GetFunctionButton` / `GetFunctionButtonTitle` | 用意していない | 使用箇所がない。ボタンが必要なら `Bar.GetButton(キー)` |
| `AddFunctionButton` / `AddDummyButton` | 用意していない | コンストラクタの中だけで使われている。F10 のダミーは不要(4.4) |
| (なし) | `On(FuncKeyDefine, Action)` | 新規。5.4 |

### 5.6 FormFrame との関係

- `FormFrame` に、フィールド `protected FunctionKeyBinder funcKeys = null;` を追加した。`FormFrame` 自身はこのフィールドを参照しない。
- そのため、`funcKeys` が null のまま(置き換えていないフォーム)でも、`appFuncKey` と両方が設定されていても、`FormFrame` の動作は変わらない。
- 置き換えたフォームでは `appFuncKey` が null のままになる。`FormFrame` は `appFuncKey` を null チェックしてから使っているので問題ない。
- `FormFrame` を継承していないフォーム(`GlassBackdropForm` の派生など)でも、フォーム側にフィールドを持てば同じように使える。

## 6. 既存フォームの置き換え手順

1 フォームあたりの作業:

| # | ファイル | 作業 |
| --- | --- | --- |
| 1 | `○○.Designer.cs` | `funckey` の型を `GrapeCity.Win.Bars.GcFunctionKey` から `ComponentSUI.FunctionKeyBar` に変える(宣言と `new` の 2 か所)。`funckey.ImageScalingSize` と `funckey.Text` の行があれば消す |
| 2 | `○○.Designer.cs` | 帯が高くなる分(25 → 66)、`funckey.Size` の高さを 66 に、フォームの `ClientSize` の高さを +41 にする |
| 3 | `○○.cs` | `appFuncKey = new AppFunctionKey(...)` を `funcKeys = new FunctionKeyBinder(...)` に変える |
| 4 | `○○.cs` | `appFuncKey.SetEnabled` / `SetVisible` を `funcKeys.` に変える(該当するフォームのみ)。変え忘れると、`appFuncKey` が null なので実行時にエラーになる |
| 5 | `○○.cs` | `Func○○.△△.Execute = メソッド;` を `funcKeys.On(Func○○.△△, メソッド);` に変える(推奨。後回しにもできる) |

既存ファイルを編集するときは、そのファイルの改行コードを変えない(`FormFrame.cs` のように LF のファイルがある)。

## 8. 決定事項の記録

| 項目 | 決定 |
| --- | --- |
| 右寄せにするキー | ボタン 1 つは右、2 つは左と右。3 つ以上はキーボード上の近さで左右に分ける(5.2)。F11 は F12 に近いので右、F6 は F5 に近いので左 |
| 文字の大きさと間隔 | 名称は 9.5pt。バッジと名称の間は 5(実画面を見て、10.5pt・間隔 2 から変更) |
| ボタンの中身の並べ方 | 2 段(キー名が上、名称が下)。横並びでは FormKaiin の名称が収まらなかったため。収まらない場合は文字を自動で小さくする(4.3) |
| 強調するボタン | EnumName が `Exec` / `Save` / `Entry` のもの(5.3) |
| 帯の高さ | 66。置き換えるフォームは高さを 41 広げる(当初は 52 / +27。基本情報の実画面を見て、余白を増やし区切り線を追加した) |
